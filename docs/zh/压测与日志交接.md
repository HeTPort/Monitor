# 压测方案与日志交接

## 目标和统计口径

在实际可用板卡上运行用例，记录显式错误、正确性校验、超时、吞吐和观察到的温度/频率变化。阶段由测试目的划分，执行日期、重复次数与持续时长按现场安排，不预设固定周期。工具不控制电压/频率，也不由运行通过推导最低稳定电压。

实际测量秒数来自设备原生 summary。主机等待、初始化、预热、golden 生成与 null/fake 框架测试不代替真实压测。空白模板不是实测记录。阶段编号与日历日期分别记录。

## 用例安排

| 阶段 | 用例 | 检查重点 |
|---|---|---|
| 接板与基础链路 | CPU/GPU smoke；可用时 NPU smoke | 身份、UART、FINAL、完整收集与哈希 |
| CPU 定向负载 | integer、floating_point、matrix、memory | 首错、工作计数、线程、实际频率 |
| GPU 图形路径 | light/mid/heavy；有参考时 ALU/SFU/texture/fill | 驱动、等待、读回、图像基准 |
| NPU 模型 | kws01/ic01/ad01/sww01 load | 实际后端、模型/输入、依赖与位置证据 |
| 持续与升温 | CPU/GPU thermal | 温度趋势、降频、吞吐变化、散热条件 |
| 高强度与切换 | CPU burst/extreme、GPU extreme | 瞬态变化、无进展、超时和恢复现场 |
| 回归复核 | smoke、正确性配置与故障复现项 | 未执行项、失败/跳过、证据完整性 |

无 NPU runtime/delegate 时记录跳过；其他模块的运行不能替代 NPU 覆盖。严格 GPU 图像校验或 NPU 资格化缺少必需参考时跳过并说明原因，不降低校验配置后沿用原结论。

## 沿用公共流程执行

每项按[使用指南](使用指南.md)执行 validate/probe/pair/deploy/verify-deployment/run/collect/report。多个模块用不同 profile 和 test/attempt；串口必须独占。更换板卡单独登记 board_id，不把多块板数据合并成单板稳定性结果。

可选 `stress` 将这些命令串行组织起来，和普通 run 使用同一套部署、判定、收集与报告实现。它已经接入可执行文件，不需要另装 Python。复制发布配置中的 `soak/stress.example.json` 和 `soak/board.example.json` 到可写位置，再填写真实参数：

```powershell
# $MON 为实际 vmin_judge.exe 路径
& $MON stress validate-plan --plan 'D:\Stress\plan.json'
& $MON stress run --plan 'D:\Stress\plan.json' --board 'D:\Stress\board.json' --campaign 'D:\Stress\CAMPAIGN_A' --stage 1 --prepare --dry-run
& $MON stress run --plan 'D:\Stress\plan.json' --board 'D:\Stress\board.json' --campaign 'D:\Stress\CAMPAIGN_A' --stage 1 --prepare
& $MON stress summarize --campaign 'D:\Stress\CAMPAIGN_A'
```

先 dry-run 检查计划命令，再实际运行。`--stage` 选择计划阶段，不是日期；计划可只保留需要的阶段并从 1 顺序编号。`cycles` 控制每阶段循环次数。`--prepare` 明确执行 deploy；不传则只核验已部署资产。自定义 profile 可填绝对路径，或相对 board.json 的路径；命名 profile 使用程序资源/外置配置解析。

| board 配置 | 填写说明 |
|---|---|
| board_id / board_model / board_serial | 短英文数字编号、真实型号、实际序列号 |
| device / transport / pc_serial | HDC/ADB ID、hdc/adb、PC 串口 |
| device_uart / baudrate | 可选设备 UART 与真实波特率；省略时依平台/配对 |
| platform / available_targets | 实际平台名、明确可用 cpu/gpu/npu |
| npu_delegate_ready | 只有依赖实际准备好才设 true |
| golden_by_profile / baseline_by_profile | 每 profile 的参考路径或批准基线 ID；同项互斥 |
| frequency_note / operator | 外部锁频设置、读数证据及操作者 |

默认遇失败停止。处理后续跑会跳过已完成且收集完整的项；失败或跳过项重试要显式 `--retry-failed`，继续其他项可用 `--continue-on-error`。原失败记录仍保留。配置变化会形成新的执行身份。每个 campaign 使用独立状态目录保存配对和基线；使用 baseline 时须先将批准基线导入该状态目录，golden 路径则按 board 配置读取。

脚本不自动注册任务、唤醒主机或安排并行压测。主机休眠、断电、超时与人工停止都要记录。异常退出残留 `.runner.lock` 时，先确认原执行器与板端进程已停止，再按现场规程处理锁，不要直接启动第二个进程抢串口。

## 记录与证据目录

```text
CAMPAIGN_A/
  configuration/     计划与板卡配置快照
  operations/        每阶段命令、返回码、stdout/stderr、超时
  runs/BOARD_A/      PC 运行结果与 device-evidence 收集目录
  state/BOARD_A/     本次压测配对与基线状态
  ledger.jsonl       追加台账，失败、跳过、重试均保留
  summary/           stress-summary.json、压测汇总.md
```

| 文件/事件 | 要看什么 | 异常处理 |
|---|---|---|
| 构建与部署清单 | 目标架构、命令、产物 SHA、配置与完整资产 | 主机产物不能冒充板端产物；哈希不符先定位资产 |
| run-manifest.json | test/attempt、profile/参考、预算与设备路径 | 确认同一会话，不混入其他运行 |
| result.json | verdict、exit_code、DUT/infrastructure 原因 | 分开硬件/计算故障与传输/依赖错误 |
| workload.log | 首次 error、verify FAIL 及上下文 | 保留原始输出，不能仅交最后一行 |
| workload-summary.json | duration、工作量、verify_count/fail、result | 缺失或计数矛盾不能认作完整合格样本 |
| heartbeat | 最后阶段、时间和实际进展计数 | 区分日志节流与真实无进展 |
| final.json | 身份、summary_seen、退出码、timed_out | summary 与 FINAL 必须一致闭环 |
| telemetry.jsonl | 频率、温度、利用率、complete/缺样 | 记录真实接口；未知值不填零 |
| stderr / diagnostics | API/驱动、依赖、厂商分区信息 | 保留首次故障与运行位置依据 |
| relay.log / serial.raw | CRC、序号、身份、帧长、尾部 | 链路错误不能直接认作芯片算错 |
| artifact-hashes.json | 应收文件与 SHA-256 | 缺少或不符应标证据不完整 |
| operations / ledger | 开始结束、命令、失败、跳过、重试 | 结果必须回链原始现场 |

## 交接记录模板

每次记录实际开始/结束、板卡、profile、目标模块、实际测量时长、校验方式、判定、收集哈希、异常/跳过原因、供电/散热/外部频率设置、证据路径与操作者。表格实际输入栏为空，按日志填入；不能从计划推算已经完成的时长。

汇总按实际执行范围说明已运行哪些用例、真实负载多久、有哪些校验失败/超时/降频、哪些未执行及原因。真实日期覆盖不等于连续运行时长，重试不能抹去首错。不要只交 report.md，应交完整证据目录及配置快照。

需要 hilog、dmesg、厂商 GPU/NPU trace 或仪器功耗记录时，按目标系统已验证的方式另行导出，写明实际命令、时间窗口和文件哈希。未采集就记录“未采集”。改变电源、线缆、散热或锁频条件时记下时间，便于解释性能变化。
