# 七天压测执行与日志交接

## 验收口径

本计划按“连续七个日历日中的用例运行记录”设计，不预设每天 24 小时。每天的真实执行时间、板卡和可用后端都需记录。随机拿到的板卡先识别再选择用例，不支持的目标写 SKIP 与原因。没有调压接口，本周只报告运行稳定性、显式错误、超时、温度/频率和吞吐变化；不报告最低稳定电压。

当前提供的是计划、执行工具和空白记录，尚未发生的七天压测不会被填成已有结果。主管周报中的测量秒数来自设备 native summary；程序等待、预热、golden 生成、null/fake 后端不代替实际压力时长。七个 Day 编号若实际在同一天执行，汇总仍只显示一个实际日历日期。

## 执行前准备

1. 选择真实板卡，登记型号/SoC、设备 ID、板号/序列号、系统 build、驱动、供电、散热、操作者与主机时间。每换板卡使用新的 board_id；不能把两块板的数据归成同一块。
2. 完成 SDK 编译和 tools 资产准备，核对 capabilities contract=2。NPU runtime/delegate 未准备时，load/qualification 写跳过，不以 null 替代。
3. 复制 platform/profile 适配实际板卡。现有模板是 Kirin9030/Kirin9020，其他板卡必须有匹配的身份/串口/遥测信息。
4. 复制 `config/soak/board.example.json`，填写 device、pc_serial、platform、available_targets。不要把示例 FILL_* 当实际参数。已在外部锁频时，将设置方法、期望频点、实际频率记录路径写入 frequency_note；工具不执行锁频。
5. 复制 `config/soak/week.example.json`，选择可用 profile 和每日 cycles。增加循环数会增加重复运行，但不承诺热稳态、连续性或 168 小时。需要更长单次持续用例时，另建 profile、修改原生 timeout 与 Monitor runtime budget，再重新部署核验和重新绑定参考。
6. 严格 GPU golden-image 和 NPU qualification 准备各自同配置参考。在 board 配置的 golden_by_profile 或 baseline_by_profile 中指定，二者互斥。没有参考就记录跳过，不能降低校验模式后沿用原结论。

## 七天建议安排

| 天 | 重点 | 建议用例 | 当天检查 |
|---|---|---|---|
| 1 | 接板和基础链路 | CPU/GPU smoke、NPU KWS smoke（若可用） | 身份、UART、FINAL、完整收集和哈希 |
| 2 | CPU 定向路径 | integer/floating_point/matrix/memory | 每项计数、首次 verify、线程和实际频率 |
| 3 | GPU 负载层次 | light/mid/heavy；有 golden 时 ALU/SFU/texture/fill | 驱动错误、hang、host/device timing、图像基准 |
| 4 | NPU 模型 | 四模型 load；无运行库时 CPU 混合补充 | runtime/delegate 版本、位置证据、模型与输入 SHA |
| 5 | 持续和升温 | CPU thermal、GPU thermal | 温度斜率、降频、吞吐随时间变化、散热条件 |
| 6 | 高强度和切换 | CPU burst/extreme、GPU extreme | 无进展、超时、工作量是否适配、故障后的现场 |
| 7 | 回归和复核 | smoke、mixed correctness、可用 NPU | 重放、缺失文件、哈希、失败/跳过闭环与周报 |

示例计划每项默认一次，属于覆盖起点。若主管要求 7×24，请先明确每块板允许的条件、可连续运行时长和故障处置，再提高循环/时长并安排值守；不能把本计划默认执行量标为 168h。

## 脚本操作

从 Monitor 目录执行。Windows 和 Linux 使用相同参数（Linux 通常 `python3`）。`--prepare` 表示明确执行部署；不指定时只核验已经部署的资产。

```powershell
python scripts/soak.py validate-plan --plan config/soak/week.example.json
python scripts/soak.py run-day --plan MY_WEEK.json --board MY_BOARD.json --campaign output/CAMPAIGN_01 --day 1 --prepare --dry-run
python scripts/soak.py run-day --plan MY_WEEK.json --board MY_BOARD.json --campaign output/CAMPAIGN_01 --day 1 --prepare
python scripts/soak.py summarize --campaign output/CAMPAIGN_01
```

每天在实际日期运行对应 `--day 2` 至 `--day 7`。脚本不注册定时任务，不自动跨七天唤醒主机，也不自动启动并行 CPU/GPU/NPU。不要通过同一串口同时启动多个 campaign。

默认遇到失败停止。检查现场后可再次运行同一命令：已完成且证据完整的项跳过；重试失败或先前跳过项需 `--retry-failed`。确需继续剩余用例时用 `--continue-on-error`，但它不会清除失败记录。计划或板卡配置变化会形成新的执行身份，应在交接说明中写清原因。

主机超时或强制中止时，必须检查设备进程是否已停止并收集原 attempt。`.runner.lock` 防止同一 campaign 并发执行；异常退出留下锁时，应先确认原进程和设备已停止，再人工移走锁，不能自动删除运行中锁。

## 目录和留存

```text
CAMPAIGN_01/
  configuration/     计划与板卡配置快照
  operations/        每阶段 argv、返回码、stdout/stderr、超时现场
  runs/BOARD_A/      PC result、run-manifest、UART 原始捕获、完整事件
    TEST_ID/device-evidence/ATTEMPT_ID/spool/
  ledger.jsonl       追加台账，失败和重试均保留
  summary/           weekly-summary.json 与中文周报
```

不要只交 report.md。交付整个 campaign，并另带构建 manifest、二进制哈希、vendor diagnostics 和锁频/散热条件记录。每天检查剩余磁盘空间、设备 spool 空间、主机是否睡眠、USB/UART 是否掉线；变更线缆/电源/散热也要记录时间。

## 重点日志和记录

| 文件或字段 | 必看内容 | 发现异常时的含义 |
|---|---|---|
| build-manifest.json | target/架构、源码提交、dirty、命令、编译器、SHA | 编译成功与板端兼容是两件事；不同产物不可混算 |
| deployment-manifest.json / preflight | 本地/远端哈希、完整资产、能力、NPU 库身份 | 哈希不符或依赖错误先归基础设施问题 |
| run-manifest.json | test/attempt、profile/baseline、timeout、设备路径 | 关联一次运行的全部证据，不与其他会话混用 |
| result.json | verdict、exit_code、DUT/infrastructure reasons、liveness | PASS 需配合原始证据；不能只统计进程返回 0 |
| workload.log | 全部原生 JSONL 和故障附近输出 | 看首次 error/verify FAIL，不能只取最后一行 |
| workload-summary.json | result/exit、实测 duration、工作单元、verify_count/fail | 计数缺失/矛盾或无 summary，不能当有效通过 |
| verify 事件 | pass/result、首错单元、checksum/golden | 明确失败立即留存，成功采样少不代表校验少 |
| heartbeat | 最后时间、phase、work unit 进展 | 进展停住与日志被限流需区分；无进展不能靠定时心跳掩盖 |
| final.json | summary_seen、workload_exit_code、timed_out、身份 | workload summary 与 agent 完成一致才算链路闭合 |
| telemetry.jsonl | 实际频率、温度、利用率、缺样/节流 | 有锁频设置也需验证实际读数；未知数据不可补 0 |
| workload-stderr / diagnostics | 初始化、API/驱动错误、厂商 NPU 信息 | 定位依赖、GPU hang 或 NPU 委派问题 |
| relay.log / raw UART | 帧过长、CRC/序号/身份、FINAL 尾部 | 传输错误不等同计算结果错误 |
| artifact-hashes.json | 应收文件与 SHA-256 | 缺失或不符的证据不能由报告补齐 |
| operations 与 ledger | 实际时间、命令、错误、重试、跳过和操作者动作 | 保留运行过程，避免只保留成功的一次 |

## 日报和周报模板

日报应记录：实际日期、板卡与条件、计划项、执行次数、有效测量秒数、完整证据通过数、失败/中断、跳过及原因、故障处理、证据路径和责任人。没有测量依据的时长留空/缺失，不填成零时长成功或满时长完成。

周报应包含七天逐日表、真实日历覆盖、按板卡/target/profile 的范围、异常及复现进度、未执行项、版本变化、证据目录和结论边界。脚本的周报只按实际 ledger 汇总，不从计划推算完成率。手工 Excel 模板中的记录也要回链原始日志。

建议结论：在所列板卡与条件下完成哪些用例、实际运行多久、观察到哪些错误/超时/降频、还有哪些缺口。不要写“全部 AVS 验证通过”或“全周 168h 稳定”而没有相应条件和测量记录。

## 平台系统日志的补充

常规链路不自动完整抓取所有 hilog、dmesg、厂商 GPU/NPU trace 或电源轨仪器数据。需要时用目标系统已验证的导出方式单独保存，记录实际命令、时间窗口、工具版本与文件哈希；没有采集应写“未采集”，不能推导成“无内核/驱动错误”。该部分与 workload 原始 stderr/diagnostics 一并交接。
