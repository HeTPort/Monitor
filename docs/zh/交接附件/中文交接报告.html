原生内置 profile 与 Monitor 配置的区别

CPU 原生名称：idle、integer、floating_point、matrix、memory、mixed、burst、thermal、stress_extreme。前六类分别对应空闲/整数/浮点/矩阵/内存/混合实现；burst 通过占空比交替，thermal 和 stress_extreme 通过持续时长及工作量增强。

GPU 原生名称：idle、ui_burst、game_light、game_mid、game_heavy、alu、sfu、texture、fill、mixed、burst、thermal、stress_extreme。原生 API 默认 null；idle/ui_burst/burst 及 game_light 的分数占空比不能直接用于当前 Vulkan 后端。Monitor 中的 light/mid/heavy 重新固定 duty_cycle=1。ALU/SFU 原生默认 compute，而 Monitor 明确改为 offscreen。不能仅看同名 profile 就认为后端或覆盖相同。

NPU 原生名称：kws01、ic01、ad01、sww01、framework_smoke。每个真实模型在 Monitor 中分 smoke、load、qualification 三类，后三种类别的证据要求不同。framework_smoke 仅是测试夹具。

使用选择

  • 初接板卡先跑对应 smoke，核对退出码、FINAL、完整收集和哈希。
  • 先跑一般 CPU/GPU 负载，再运行整数/浮点/矩阵/内存及 GPU 各 shader；每项保留单独 test/attempt。
  • 热稳态或突发用例与稳态性能基线分开统计；吞吐波动不是自动等同计算错误。
  • NPU 先核实运行库和厂商执行位置。没有运行库时记录跳过；null 结果不能填作 NPU 压测完成。
  • 未准备严格 golden 的 GPU 用例应跳过并记录原因；不能悄悄改成 verify_mode=none 后沿用正确性结论。

Windows Linux 统一编译指南

入口和目标

在 workload 根目录使用 build.ps1（Windows PowerShell）或 build.sh（Linux/WSL），统一参数由 scripts/build.py 解析。CPU/GPU/NPU 源码已在同一交接分支中统一，不再选择另外一份旧协议源码。各子项目旧入口保留，集中入口为交接时推荐入口。

参数用途
--components 'cpu,gpu,npu'选择组件；还可选 relay、monitor；all=三类 workload 加 relay
--target host当前主机架构，不能部署成 Android/OHOS ARM64
--target android-arm64Android NDK 交叉编译，需 CMake/toolchain
--target ohos-arm64OpenHarmony/HarmonyOS NDK 交叉编译，需 CMake/toolchain
--engine auto/cmake/directauto 优先 CMake；host 可使用 g++/clang++ 直接编译
--gpu-apis 'null,vulkan'显式选择 GPU 后端；默认 null 只做框架验证
--configuration Release/Debug优化/调试构建，分别记录输出
--ndk-root PATH也可使用 ANDROID_NDK_HOME 或 OHOS_NDK_HOME
--compiler PATH / --c-compiler PATHdirect 模式的主机 C++/C 编译器
--generator Ninja指定 CMake generator
--cmake-arg=-DNAME=VALUE传递 SDK、库或项目专属 CMake 参数
--test执行短主机检查；交叉编译目标禁止在主机执行
--doctor检查本次选择需要的环境，不运行编译器
--dry-run生成 planned 构建计划；不产生成功产物或伪造哈希
--monitor-root PATHMonitor 目录，默认 sibling npu-monitor

PowerShell 中组件列表建议加引号，避免逗号被解释为数组。Windows 没有 POSIX termios，不能构建原生 Windows relay；用 WSL 的 host 自检或安装 NDK 后构建板端 relay。

主机环境

Windows 需要 Python 3.10+ 和可用的 C++17 编译器（例如 MSYS2 UCRT64 的 g++）；使用 CMake 时还需对应 generator/build tool。Linux 需要 Python 3、g++/clang++，relay 需要 cc/gcc/clang。运行 Monitor 测试需要 requirements.txt/requirements-dev.txt 中的 Python 依赖。

$env:PYTHON = 'C:\Path\To\python.exe'
.\build.ps1 --components 'cpu,gpu,npu' --target host --engine direct --doctor
.\build.ps1 --components 'cpu,gpu,npu' --target host --engine direct --test
PYTHON=python3 sh build.sh --components cpu,gpu,npu,relay --target host --engine direct --test

默认 GPU=null、NPU 的 native 测试=null/fake runtime。它们用于配置、生命周期和协议检查，不能当作实际 GPU/NPU 板端压测。--test 的 GPU 自检需保留 null 后端；编译真实 Vulkan 可同时启用 null,vulkan。

Android 和 OHOS 目标

目前交接机器没有两类 NDK，以下为配置好环境后的入口，尚未在本机完成交叉编译验收。缺失 SDK/toolchain 会明确失败，不会偷偷生成 host 程序冒充 ARM64。

$env:ANDROID_NDK_HOME = 'C:\SDK\android-ndk'
.\build.ps1 --components 'cpu,npu' --target android-arm64 --engine cmake --generator Ninja
$env:OHOS_NDK_HOME = 'C:\SDK\ohos-sdk'
.\build.ps1 --components 'cpu,gpu,npu,relay' --target ohos-arm64 --engine cmake --gpu-apis 'null,vulkan' --generator Ninja
export OHOS_NDK_HOME=/opt/ohos-sdk
sh build.sh --components cpu,gpu,npu,relay --target ohos-arm64 --engine cmake --gpu-apis null,vulkan --generator Ninja

CPU/NPU 使用各自 CMake toolchain；GPU 使用统一后的 standalone CMake。GPU 真后端还需要目标 SDK 的 EGL/GLES/Vulkan/OpenCL 头文件和库；Vulkan shader 构建需主机 glslangValidator。Android/OHOS 的双框架工程若在其他仓库，需要独立核对，不能把本入口当作该工程的替代品。

relay 使用目标 NDK clang/sysroot。脚本按 Android 的 LLVM prebuilt 或 OHOS native/llvm 布局定位；SDK 布局不符会拒绝执行，应核对实际 SDK 后调整，而不是套用主机 cc。

NPU 的编译不需要厂商库参与链接（运行时动态加载），但真实推理必须在板端具备 TFLite C runtime、厂商 delegate 和依赖库。构建成功不代表这些库存在或能运行。

输出、部署和版本

每次输出独立目录：build/unified/<target>/<configuration>/<UTC时间-随机ID>/。其中有每组件日志、实际 binary、build-manifest.json，记录命令 argv、源码提交和 dirty 状态、host/target、NDK 路径、返回码、产物大小和 SHA-256。failed/planned 与 success 明确区分。

只有 device target 的产物才进入 Monitor tools。不要把 host.exe 或 WSL ELF 放到手机。NPU 可使用 Monitor 的 scripts/stage_npu_assets.py 完整复制四模型；CPU/GPU 二进制、SPIR-V 和 relay 分别按平台配置准备。之后执行 --capabilities、deploy、verify-deployment；协议必须为 2。保留构建 manifest 与设备部署 manifest，作为源码到板端文件的对应依据。

Monitor 打包可选 --components monitor --target host --monitor-root PATH，依赖当前主机 Python 的 PyInstaller、pyserial、PyYAML，以及已准备的 release assets。它只生成当前主机的 Monitor 包；首次交接建议先执行 Monitor 的 validate --package 和原有打包脚本的完整检查。设备 workload 和主机 Monitor 的架构是不同维度。

压测工具使用指南

先确认目标

这份指南用于手头板卡的负载运行和稳定性观察。记录 SoC/板卡型号、序列号、系统/驱动版本、供电和散热、操作者、是否已有外部锁频。工具不提供调压/锁频/休眠控制。不同板卡不能仅因为“都能 hdc 连接”而共用 Kirin9030 的身份、串口和遥测配置。

安装和目录

Monitor 主机依赖在 requirements.txt 中。把对应 SDK 编出的 CPU/GPU/NPU、relay 和 shader 放入 tools 的平台配置路径。NPU 模型和输入必须连同 manifest 相对布局一起保留。负载协议统一为 2；通过各 binary 的 --capabilities 输出检查 workload 类型、模式和特性，不从文件名猜版本。

复制现有 platform/profile 到新名字后适配新板卡：身份字段来自真实设备、传输选择 hdc/adb、UART 候选和波特率按接线确认、CPU/GPU/NPU 遥测路径按实际系统核对。Monitor profile 的 platform 字段和板卡记录一致。不要仅删除 identity.required 来让错误平台通过；未知接口先标为可选/不可用，并写清影响。

一次运行的完整步骤

以下为 PowerShell 示例，设备 ID 和串口必须替换。Linux 使用相同 Python 参数，PC 串口通常是 /dev/ttyUSB*；所有全局参数放在子命令前。

python main.py validate --profile cpu_smoke_kirin9030
python main.py --transport hdc --device DEVICE_ID probe --platform kirin9030
python main.py --transport hdc --device DEVICE_ID deploy --profile cpu_smoke_kirin9030
python main.py --transport hdc --device DEVICE_ID verify-deployment --profile cpu_smoke_kirin9030
python main.py --transport hdc --device DEVICE_ID --pc-serial COM4 run --profile cpu_smoke_kirin9030 --test-id BOARD_A_D1 --attempt-id A001 --pc-artifacts full --telemetry
python main.py --transport hdc --device DEVICE_ID collect --test-id BOARD_A_D1 --attempt-id A001 --artifact-set full --verify-hashes
python main.py report --run-dir output/BOARD_A_D1/A001 --format markdown,json,csv

deploy 显式准备文件，verify-deployment 核验文件，run 只检查和执行已部署资产。更换 profile、二进制、shader、模型、输入或生效配置时重新部署核验；不要把先前用例的成功状态带入另一个用例。

每次测试使用稳定 test_id 分组、唯一 attempt_id 记录一次尝试。正式一周记录选择 --pc-artifacts full 和完整 collect，保留原始输出。脚本或命令失败时仍尽可能 collect 原 attempt；重试生成新 attempt，保留第一次失败现场。

CPU GPU NPU 的选择

CPU 先 smoke，再 integer/floating_point/matrix/memory/mixed，最后 burst/thermal/extreme。threads、iterations、working_set_kb 控制工作量；Monitor 不强制 CPU affinity，实际跑在哪些核需遥测/系统记录核实。thermal 运行长不等于已达到热稳态，观察温度斜率与降频情况。

GPU 先 smoke/load_light，再 mid/heavy、ALU/SFU/texture/fill。Monitor 当前 Vulkan 走 offscreen RGBA8，不能直接使用原生 idle/burst/compute/分数占空比设置。load-only 使用 none 时只判显式错误；有同配置可信 golden 后才能运行严格 golden-image 并作正确性判断。texture_count 的含义和 fill 对 iterations 的限制见用例总表。

NPU 先 smoke 校验资产和链路，再在运行库准备完成后尝试 kws01，再扩展 ic01/ad01/sww01。缺少 runtime/delegate 时记录未执行；不要用 null 结果替代真实 NPU。qualification 还要求外部已批准 golden、逐次校验和绑定的厂商执行位置证据，详见中文 NPU 专项指南。

正确性与性能

  • verify_interval 控制实际校验，不是日志间隔；verify_count 必须来自 workload 真实执行。
  • success_log_interval 控制成功校验事件采样，额外有每秒限流；失败立即输出。
  • summary 缺失、计数矛盾、FINAL 缺失、身份/CRC/序号错误或部署哈希错误，都不能当作合格样本。
  • 没有外部 golden 的重复一致性不等于独立正确性；none 模式不检查输出正确性。
  • CPU operations/s、GPU frames/s、NPU inferences/s 不可直接按数值比较。
  • 预热和 golden 生成不计入正式测量；device_time_valid=false 时设备耗时保持不可用。

失败和现场处理

现象先看什么处理方向
配置/部署失败validate/verify-deployment 返回、资产路径与 SHA先修资产/平台/依赖，不记录为芯片计算错误
checksum/图像不匹配首次 verify 失败、对应 golden/config/binary保留现场，核对参考身份，固定条件重复
hang/无 summary最后真实 heartbeat、workload/stderr、relay/FINAL判断 workload 卡死、驱动等待、串口或 transport 中断
吞吐下降温度/频率/利用率、host/device latency检查降频、热稳态、系统竞争和锁频是否真正生效

默认遇到失败先停，记录故障时间、板卡状态、操作者动作，再决定是否续跑。不要自动清空日志、重启后只留下成功结果，或删除设备 evidence 来节省空间。若主机进程被强制终止，需要人工核对板端进程是否确已结束。

重放和报告

压测工具设计指南

结构与责任

系统分为主机 Monitor、板端 device agent、原生 workload 和独立遥测四部分。Monitor 负责配置、身份与资产、启动事务、UART 判定和证据归档；workload 负责执行真实工作和输出原生 JSONL；agent 负责进程生命周期、完整本地留证和紧凑 UART 转发；telemetry 从平台声明的真实接口采样。外部电压/频率/系统调度不在本工具的写入控制范围。

主机 profile 与平台配置
  -> validate / probe
  -> 显式 deploy / verify-deployment
  -> run manifest 与唯一 test_id / attempt_id
  -> transport 启动板端 agent
  -> CPU batch / GPU frame / NPU inference
  -> 完整原始日志留板端，紧凑事件经 UART v2 到主机
  -> PolicyEngine 判定，collect 核验，report / 周报归档

扩展点与兼容性

src/target_adapters.py 采用静态注册表，集中描述工作单元、吞吐/延迟字段、NPU 配置及资产/执行证据差异。CPU/GPU 保留原逻辑，不为三个 target 复制三套传输或判定引擎。新增目标时先添加适配器、schema、资产解析和测试，再接入同一公共流程。

CPU/GPU/NPU 的 C++ 公共代码没有整体重构；本次将 GitHub CPU/GPU 校验分支保留历史合并到 NPU 分支，使运行接口统一。三份 verify_schedule.h 需保持一致，并由测试检查。原生事件 schema 1、verification contract 2 和 UART protocol 2 各管各的版本，不可把它们混成一个版本号。

workload 的执行模型

CPU 一次 batch 执行确定性计算；GPU 一次 frame/dispatch 提交并等待 GPU 操作，图形路径可读回图像；NPU 一次 inference 经过 Init/CreateResources/SetInputs/Submit/Wait/ReadOutputs/Destroy 生命周期。NPU 接口异步，但当前 runner 每次提交后等待完成，没有并发推理吞吐流水线。

工作量和日志是不同控制面。verify_interval 选择真实工作单元的校验点，计数只在实际校验路径增加；成功事件采样和每秒上限只限制日志。任何失败立即报告，并在 agent 侧锁存首个失败，防止后续没有 summary 时丢失。

预热不进入正式计数，golden 生成也不是持续性能样本。NPU 用预热次数，CPU/GPU 用预热秒数。吞吐保留原单位，设备时间没有有效证据时保持缺失。心跳只能代表已有进展，不能用后台定时线程把后端卡死伪装成健康。

资产与基准身份

部署清单必须能追踪 binary、生效配置、shader、manifest、模型、输入及 runtime/delegate 依赖。NPU manifest 的资产路径要受限，注册张量描述必须一致，声明 SHA-256 必须匹配。运行库可以是受管理资产或板端已安装且固定哈希的文件；不能将 Windows DLL 或主机 ELF 当作板端 SO。

生效设备路径配置与用户源码配置分别保留。修改配置/模型/输入/编译器选项/运行库后，原 golden 或性能基线是否仍匹配由 fingerprint 检查，不能靠重命名文件复用。NPU 正式参考要求生成条件和审批信息，执行位置要求独立厂商诊断绑定；无证据为 unknown。

传输和判定

设备完整 events/workload/summary/stderr/telemetry/FINAL 在 spool 留存。UART 只携带必要字段；长分区描述、模型信息不挤入单帧。COBS、CRC、序号、会话身份和 FINAL 规则共用，verification_summary 可以分片，主机合并并拒绝矛盾重复字段。

PolicyEngine 保留计算失败与基础设施错误的区别。缺依赖、部署/哈希错误、协议异常或证据不完整不应等同芯片算错；明确校验失败和 workload 失败必须保留。性能异常还要联系温度、实际频率、系统竞争和后端等待，不应仅用 throughput 下降推断硬件失稳。

集中构建和周记录工具

workload scripts/build.py 只编排编译命令，不修改计算核。它支持显式组件、host/Android/OHOS、GPU API 选择，按每次构建记录版本、命令和产物。dry-run 产物是 planned，不是 success；未配置 NDK 不回退到 host 冒充交叉编译。Monitor 打包是主机组件，与设备 binary 分开。

Monitor scripts/soak.py 是顺序执行器，不是多负载联合调度器。它显式调用 validate/可选 deploy/verify/run/collect/report，追加记录每一次尝试。只有 PASS 且收集哈希完整的结果能归入完整通过项；框架后端、主机等待、预热与缺失 summary 不补算成压力时长。续跑根据计划/板卡配置身份和完成证据判断，重试保留新记录。

维护顺序

修改配置或接口先补有意义的边界测试，再跑相关协议、资产、agent/UART 和主机回归。新增实际硬件后端必须验证真实运行位置、输出与退出、阻塞调用/清理边界，以及设备收集。代码测试、模拟 runtime、实机运行和资格化结论分别记录。原始证据不可因测试失败而删除或覆盖。

七天压测执行与日志交接

验收口径

本计划按“连续七个日历日中的用例运行记录”设计，不预设每天 24 小时。每天的真实执行时间、板卡和可用后端都需记录。随机拿到的板卡先识别再选择用例，不支持的目标写 SKIP 与原因。没有调压接口，本周只报告运行稳定性、显式错误、超时、温度/频率和吞吐变化；不报告最低稳定电压。

当前提供的是计划、执行工具和空白记录，尚未发生的七天压测不会被填成已有结果。主管周报中的测量秒数来自设备 native summary；程序等待、预热、golden 生成、null/fake 后端不代替实际压力时长。七个 Day 编号若实际在同一天执行，汇总仍只显示一个实际日历日期。

执行前准备

  • 选择真实板卡，登记型号/SoC、设备 ID、板号/序列号、系统 build、驱动、供电、散热、操作者与主机时间。每换板卡使用新的 board_id；不能把两块板的数据归成同一块。
  • 完成 SDK 编译和 tools 资产准备，核对 capabilities contract=2。NPU runtime/delegate 未准备时，load/qualification 写跳过，不以 null 替代。
  • 复制 platform/profile 适配实际板卡。现有模板是 Kirin9030/Kirin9020，其他板卡必须有匹配的身份/串口/遥测信息。
  • 复制 config/soak/board.example.json，填写 device、pc_serial、platform、available_targets。不要把示例 FILL_* 当实际参数。已在外部锁频时，将设置方法、期望频点、实际频率记录路径写入 frequency_note；工具不执行锁频。
  • 复制 config/soak/week.example.json，选择可用 profile 和每日 cycles。增加循环数会增加重复运行，但不承诺热稳态、连续性或 168 小时。需要更长单次持续用例时，另建 profile、修改原生 timeout 与 Monitor runtime budget，再重新部署核验和重新绑定参考。
  • 严格 GPU golden-image 和 NPU qualification 准备各自同配置参考。在 board 配置的 golden_by_profile 或 baseline_by_profile 中指定，二者互斥。没有参考就记录跳过，不能降低校验模式后沿用原结论。

脚本操作

从 Monitor 目录执行。Windows 和 Linux 使用相同参数（Linux 通常 python3）。--prepare 表示明确执行部署；不指定时只核验已经部署的资产。

python scripts/soak.py validate-plan --plan config/soak/week.example.json
python scripts/soak.py run-day --plan MY_WEEK.json --board MY_BOARD.json --campaign output/CAMPAIGN_01 --day 1 --prepare --dry-run
python scripts/soak.py run-day --plan MY_WEEK.json --board MY_BOARD.json --campaign output/CAMPAIGN_01 --day 1 --prepare
python scripts/soak.py summarize --campaign output/CAMPAIGN_01

每天在实际日期运行对应 --day 2 至 --day 7。脚本不注册定时任务，不自动跨七天唤醒主机，也不自动启动并行 CPU/GPU/NPU。不要通过同一串口同时启动多个 campaign。

默认遇到失败停止。检查现场后可再次运行同一命令：已完成且证据完整的项跳过；重试失败或先前跳过项需 --retry-failed。确需继续剩余用例时用 --continue-on-error，但它不会清除失败记录。计划或板卡配置变化会形成新的执行身份，应在交接说明中写清原因。

主机超时或强制中止时，必须检查设备进程是否已停止并收集原 attempt。.runner.lock 防止同一 campaign 并发执行；异常退出留下锁时，应先确认原进程和设备已停止，再人工移走锁，不能自动删除运行中锁。

日报和周报模板

日报应记录：实际日期、板卡与条件、计划项、执行次数、有效测量秒数、完整证据通过数、失败/中断、跳过及原因、故障处理、证据路径和责任人。没有测量依据的时长留空/缺失，不填成零时长成功或满时长完成。

周报应包含七天逐日表、真实日历覆盖、按板卡/target/profile 的范围、异常及复现进度、未执行项、版本变化、证据目录和结论边界。脚本的周报只按实际 ledger 汇总，不从计划推算完成率。手工 Excel 模板中的记录也要回链原始日志。

建议结论：在所列板卡与条件下完成哪些用例、实际运行多久、观察到哪些错误/超时/降频、还有哪些缺口。不要写“全部 AVS 验证通过”或“全周 168h 稳定”而没有相应条件和测量记录。

平台系统日志的补充

常规链路不自动完整抓取所有 hilog、dmesg、厂商 GPU/NPU trace 或电源轨仪器数据。需要时用目标系统已验证的导出方式单独保存，记录实际命令、时间窗口、工具版本与文件哈希；没有采集应写“未采集”，不能推导成“无内核/驱动错误”。该部分与 workload 原始 stderr/diagnostics 一并交接。
