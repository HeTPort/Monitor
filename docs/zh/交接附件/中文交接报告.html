CPU GPU NPU 工具交接报告

交接内容

本工具由主机 Monitor、板端 agent、CPU/GPU/NPU workload、串口 relay 和独立遥测组成。Monitor 以可执行文件交付使用，三类负载沿用相同的配置检查、平台探测、串口配对、部署、核验、运行、收集与报告流程。新增 NPU 通过 profile 选择，不建立另一套操作流程。

交接资料包括用例表、负载原理、可执行文件使用指南、目录结构、编译与设计说明、压测方案和空白记录表。源码目录采用相邻的 npu-monitor/ 与 npu-workload/，文档中的源码链接均指向随包文件，可离线阅读。

GPU多 API 后端、离屏渲染、算术/超越函数/纹理/填充负载目标驱动、shader、图像参考、超时与恢复

压测记录可配置阶段与循环、失败/跳过/重试留存、实际时长汇总真实板卡执行、故障现场、操作者确认

适用范围

板卡按实际可用设备选择，先适配平台与 profile 再运行。工具不调压、不锁频、不修改 governor 或绑核。已有外部锁频时记录设置及实测频率；没有相应测量与条件，不给出最低稳定电压或功耗收益结论。

已有软件检查覆盖主机编译、协议、部署与判定边界；尚无本次真实板端压测完成的结论。主机 GPU null、NPU null/fake 的结果只证明框架行为。记录表中的实际执行栏保持空白。

接手顺序

先阅读可执行文件使用指南，按原测试流程跑通一个 smoke profile。随后按用例总表和原理详解选择实际负载，按照压测与日志交接留存证据。维护者再阅读目录说明、编译指南与设计指南。

交付的运行证据应包括生效配置、产物哈希、板卡条件、平台探测、运行身份、PC 结果、设备原始日志、遥测、收集校验和故障处置记录。重试使用新的 attempt，保留首次失败。NPU 未回退不代表全部算子运行于 NPU；无可信外部 golden 时，重复一致性不代表独立正确性。

Monitor 可执行文件使用指南

1. 与原测试流程的对应关系

本指南在原用户指南、打包与设备测试计划、双板验证手册和 GPU 诊断手册的流程上补充操作说明。原文档保留不改。操作顺序仍为：

validate → probe → pair / relay probe → deploy → verify-deployment
          → run → collect → report

CPU/GPU/NPU 共用以上命令，只切换 profile。run 不会自动探测、配对或补部署。需要正确性参考时，在同一流程中增加 --golden；有批准的性能基线时使用 --baseline。普通负载先完成无 baseline 的链路检查。

环节操作目的可检查的结果
validate本地配置与发布资产检查字段合法、必需资源齐全；不连接设备
probe确认实际板卡身份和只读能力平台匹配、遥测路径是否可用
pair / relay probe确认 PC/设备串口、ABI 与 relay接线、波特率、设备串口访问和 relay 可运行
deploy部署本 profile 的全部资产文件集合、设备路径、复制/权限结果
verify-deployment只读核对已部署资产本地和设备哈希一致
run启动 agent/workload，接收 UART 并判定本次身份、真实进展、summary、FINAL、退出码
collect取回完整设备证据文件集合与哈希核验通过
report从已有 PC 结果生成报告报告可回链同一次运行

2. 安装与第一次打开

现有打包脚本生成 dist/vmin_judge.exe，它就是 Monitor。放在可正常读取且输出目录可写的位置，从 PowerShell 执行；不要求使用者安装 Python、C++ 编译器或 NDK。HDC/ADB、USB 驱动和串口驱动仍需按设备准备。主机程序和板端 workload 是不同产物：Windows 程序运行在 PC，板端程序必须符合实际 Android/OHOS ABI。

建议将发布目录、外置配置、状态和结果分开保存。示例中的 D:\MonitorRelease、设备 ID、串口均需按现场修改：

$MON = 'D:\MonitorRelease\vmin_judge.exe'
$OUT = 'D:\MonitorResults'
$STATE = 'D:\MonitorState'
$DEVICE = 'REPLACE_DEVICE_ID'
$PC_SERIAL = 'COM4'
$DEVICE_UART = '/dev/ttyHW0'
$PLATFORM = 'kirin9030'
$PROFILE = 'cpu_smoke_kirin9030'
$SESSION = Get-Date -Format 'yyyyMMdd-HHmmss'
$TEST = "BOARD_A_CPU_$SESSION"
$ATTEMPT = 'A001'
$COMMON = @('--transport','hdc','--device',$DEVICE,
  '--pc-serial',$PC_SERIAL,'--device-uart',$DEVICE_UART,
  '--output-dir',$OUT,'--state-dir',$STATE)
& $MON --help
& $MON list-profiles --target cpu

$COMMON 是 PowerShell 参数数组，所有公共参数置于子命令前。Android 设备将 transport 换为 adb；必要时把 --hdc-bin C:\SDK\hdc.exe 或 --adb-bin C:\SDK\adb.exe 加到公共参数。不要把设备序列号当成 PC 的 COM 编号。

应用默认使用内置资源；需要调整平台、profile 或 workload 时，发布人员提供可编辑的完整 config/，向 $COMMON 加 --config-dir D:\MonitorRelease\config。配置和资产还可能从当前目录、可执行文件相邻目录等位置解析；现场应固定工作目录并显式指定配置目录，避免意外命中旧文件。更改 state-dir 会切换配对与 baseline 注册信息，不要在准备和运行阶段随意换目录。

默认输出在当前工作目录的 output/。默认状态在 Windows 的 %LOCALAPPDATA%\VminJudge，缺少该环境变量时位于用户目录下 .vmin_judge。上例显式指定目录，便于交接。单文件程序内部临时解包目录由程序管理，不作为配置编辑或证据保存目录。

3. 按原准备流程检查发布包和设备

3.1 本地检查

& $MON @COMMON validate --package
& $MON @COMMON validate --profile $PROFILE

含 NPU 的发布包再执行 validate --package --include-npu。资源缺失先由发布人员补齐，不跳过检查后直接 run。源码目录里没有 tools 并不代表用户应在现场自行编译；应接收包含所需板端资源的发布包。

3.2 平台和 relay

& $MON @COMMON probe --platform $PLATFORM --full
& $MON @COMMON --json relay probe --platform $PLATFORM
& $MON @COMMON pair --platform $PLATFORM --verify

首次尚未部署 relay 时，relay 检查可能报告资产不可用；先确认 ABI，再部署，然后复查。平台身份不匹配应停止，不能删去身份要求强行通过。手头板卡不属于现有平台时，需要维护者配置真实身份、串口和遥测路径；仅修改 profile 名称不构成适配。

3.3 部署与核验

& $MON @COMMON deploy --profile $PROFILE
& $MON @COMMON verify-deployment --profile $PROFILE
& $MON @COMMON --json relay probe --platform $PLATFORM --check-uart

设备默认根目录为 /data/local/tmp/avs。不同 profile 的专属配置需要分别部署。更换 workload、shader、模型、输入、运行库或配置后，重新 deploy/verify；只换 PC exe 不会自动更新设备文件。GPU shader 必须是实际后端所需文件，NPU 必须保留 manifest 与模型/输入相对结构。

4. 三个模块采用相同 run/collect/report

先执行已部署的短用例：

& $MON @COMMON run --profile $PROFILE --test-id $TEST --attempt-id $ATTEMPT --pc-artifacts full --telemetry
$RUN_EXIT = $LASTEXITCODE
& $MON @COMMON collect --test-id $TEST --attempt-id $ATTEMPT --artifact-set full --verify-hashes
$COLLECT_EXIT = $LASTEXITCODE
& $MON @COMMON report --run-dir "$OUT\$TEST\$ATTEMPT" --format markdown,json,csv

即使 run 失败，也执行 collect 保存现场；运行退出码与收集退出码分别记录。--pc-artifacts full 保留原始串口和完整规范化事件；默认 result 模式只留紧凑结果。正式交接推荐 full。没有部署遥测或平台未满足采样条件时先修复；不能为取得 PASS 隐瞒采样缺口。

模块首次链路检查后续真实负载额外前提
CPUcpu_smoke_kirin9030cpu_stress_kirin9030；各定向 profile板端 CPU 产物与平台匹配
GPUgpu_smoke_kirin9030gpu_load_light/mid/heavy_kirin9030实际 GPU 驱动和 Vulkan shader
NPUnpu_kws01_smokenpu_kws01_load，随后 ic01/ad01/sww01_load真实 TFLite runtime、厂商 delegate 与依赖

切换模块时修改 $PROFILE、$TEST，重新执行第 3.3 节及本节。CPU/GPU smoke 在当前配置中使用真实计算/图形后端，但不进行正确性校验；NPU smoke 使用 null，只验证资产与框架，不能计为真实 NPU 压力。四模型及所有参数见用例总表。

test_id 是一组测试名称，attempt_id 标识一次尝试。每次尝试必须唯一，不能复用非空结果目录。也可不传 attempt，交给工具生成；或用 --repeat N 创建独立尝试，--repeat 与显式 attempt 互斥。重复次数不会改变单次 workload duration；每次初始化和预热之间存在间隔。

5. 结果与退出码

退出码verdict操作含义
0PASS本次配置要求下未触发失败；仍需完整收集
1DUT_FAIL明确 workload/校验失败，先保留首错
2SILENT_FAILURE无有效进展或静默超时；定位 workload、驱动与链路
3INFRA_ERROR传输、证据、依赖或运行设施错误
4INVALID_CONFIGURATION配置/资产准备不合法
5UNSUPPORTED平台或能力不满足要求
6USER_ABORT操作者中止；确认设备进程和现场

命令行拼写错误也可能由参数解析器返回 2，应结合输出及 result.json 判断，不能仅按数字认定硬件挂死。PASS 的含义受校验模式影响：none 只判显式错误；checksum 无外部参考时可能只证明运行内一致；golden-reference 不包含性能阈值；baseline 才施加批准的性能要求。monitor 串口诊断的 NOT_EVALUATED 不等于 PASS。

6. 证据位置和收集选择

PC 指定 OUT/
  TEST_ID/ATTEMPT_ID/       result.json、run-manifest.json、报告
                          full 模式额外保存 events.jsonl、serial.raw 等
  TEST_ID/device-evidence/ATTEMPT_ID/spool/  collect 取得的设备证据
设备 /data/local/tmp/avs/tests/TEST_ID/ATTEMPT_ID/
                          原始 workload/events/summary/FINAL、哈希、遥测

以命令返回的实际路径为准。collect --test-id ID 可取该组全部 attempts；指定 attempt 可按目的选择 minimal/calibration/failure/protocol。交接建议 full 并 --verify-hashes。默认保留设备文件；需要清理时先核实 PC 全量副本和哈希，再明确使用 --remove-remote-after-verify。证据子集不能用来清理设备全量文件。

重点检查 workload.log 首次 error/verify FAIL、原生 summary 的实际工作量和校验计数、final.json 的完成状态、artifact-hashes.json 与遥测完整性。SUMMARY 与 FINAL 是不同事件，只有 summary 不能证明 agent/传输完成。完整字段与异常处理见压测与日志交接。

7. 保持原有正确性与基线流程

普通压力不传 baseline；需要正确性参考时仍沿用原流程：

已知良品条件 → golden → deploy/verify --golden
 → run --golden --telemetry → collect → calibrate
 → 审阅并 baseline approve → deploy/verify/run --baseline

golden 的短运行不能作为持续性能样本。CPU 以 checksum 为参考，GPU 以同配置读回图像为参考，NPU 以可信外部 checksum 为参考并要求厂商执行位置证据。更换配置/模型/输入/后端/运行库后，旧参考可能不再适用；按实际身份重新生成与核验。

CPU 示例（GPU 用相同命令把 cpu 换成 gpu，并选对应 profile）：

$QUAL = 'cpu_qualification_kirin9030'
& $MON @COMMON deploy --profile $QUAL
& $MON @COMMON verify-deployment --profile $QUAL
& $MON @COMMON --json golden cpu --profile $QUAL --board-id BOARD_A --known-good --runs 1 --qualification-id "GOLDEN_$SESSION"
# 使用输出中实际的 golden manifest 路径
$GOLDEN = 'D:\MonitorResults\REPLACE_GOLDEN_MANIFEST.json'
& $MON @COMMON deploy --profile $QUAL --golden $GOLDEN
& $MON @COMMON verify-deployment --profile $QUAL --golden $GOLDEN
& $MON @COMMON run --profile $QUAL --golden $GOLDEN --telemetry --pc-artifacts full --test-id "CAL_$SESSION"
& $MON @COMMON collect --test-id "CAL_$SESSION" --verify-hashes

这只演示参考与持续样本的衔接，不构成已完成生产校准。离线校准 --run-dir 必须来自足量合格持续样本；现有生产策略要求至少两板和足量接受样本，不能用单板一次运行替代。baseline 未批准不可作为正式限值使用。

NPU 同样从 deploy/verify 开始；生成 golden 的命令为 golden npu --profile npu_kws01_qualification --runs N --board-id BOARD_A --known-good --approver 姓名 --conditions "实际可信运行条件与诊断引用"。准备外部参考与 placement_evidence 后，后续 run/collect/calibrate/baseline 仍沿用公共流程。没有厂商库时跳过真实负载；没有位置证据时不能把 qualification 标记为合格。NPU manifest/运行库配置由维护者按目录说明定位调整。

8. 遥测、超时和长压

独立遥测沿用 telemetry run --profile P --test-id ID --duration 60 --interval 5，不用 UART 判错链路；之后 collect。伴随 workload 使用 run --telemetry，遥测留在设备文件，不填入串口帧。检查 complete、required 指标和实际频率/温度；缺数据不能补零。

延长单次负载需在外置 workload JSON 调整 duration、timeout 和相应 runtime_budgets，执行 validate/deploy/verify 后运行。仅增加 --overall-timeout 只增加等待预算，不会增加计算时长。CPU/GPU warmup 是秒，NPU warmup_inferences 是次数。单次操作必须能在心跳静默预算内报告真实进展；不要把无限等待当成正常长压。

常规逐条命令足以完成压测。可选批量入口 stress 只是顺序调用上述同一流程，使用方法见压测方案。它不调压、不同时启动多负载，不代替平台适配。

9. 故障处理与离线复核

现象优先检查后续动作
找不到 HDC/ADB/设备指定工具路径、设备 ID、驱动与授权修复连接，再 probe；不要判芯片计算失败
串口忙/无 STARTCOM、接线、设备 UART、波特率、其他串口软件停止占用软件；不要让 monitor 与 run 同时占口
部署哈希不符当前 profile、生效配置、设备文件保留输出，重新准备资产，不隐式跳过核验

离线复核仍使用同一程序：

& $MON @COMMON simulate --events 'D:\Evidence\events.jsonl' --profile $PROFILE
& $MON @COMMON simulate --raw-serial 'D:\Evidence\serial.raw' --profile $PROFILE
& $MON @COMMON report --run-dir "$OUT\$TEST\$ATTEMPT" --format markdown,json,csv

重放不补齐原来缺失的设备证据。系统 hilog/dmesg、厂商 trace 和仪器功耗记录需使用现场已验证的方法另行导出；工具未采集这些记录时应明确写“未采集”。发生强制中止后先确认板端进程已结束，保留首次故障与失败 attempt，再创建新 attempt 复测。

压测方案与日志交接

目标和统计口径

在实际可用板卡上运行用例，记录显式错误、正确性校验、超时、吞吐和观察到的温度/频率变化。阶段由测试目的划分，执行日期、重复次数与持续时长按现场安排，不预设固定周期。工具不控制电压/频率，也不由运行通过推导最低稳定电压。

实际测量秒数来自设备原生 summary。主机等待、初始化、预热、golden 生成与 null/fake 框架测试不代替真实压测。空白模板不是实测记录。阶段编号与日历日期分别记录。

用例安排

阶段用例检查重点
接板与基础链路CPU/GPU smoke；可用时 NPU smoke身份、UART、FINAL、完整收集与哈希
CPU 定向负载integer、floating_point、matrix、memory首错、工作计数、线程、实际频率

沿用公共流程执行

每项按使用指南执行 validate/probe/pair/deploy/verify-deployment/run/collect/report。多个模块用不同 profile 和 test/attempt；串口必须独占。更换板卡单独登记 board_id，不把多块板数据合并成单板稳定性结果。

可选 stress 将这些命令串行组织起来，和普通 run 使用同一套部署、判定、收集与报告实现。它已经接入可执行文件，不需要另装 Python。复制发布配置中的 soak/stress.example.json 和 soak/board.example.json 到可写位置，再填写真实参数：

# $MON 为实际 vmin_judge.exe 路径
& $MON stress validate-plan --plan 'D:\Stress\plan.json'
& $MON stress run --plan 'D:\Stress\plan.json' --board 'D:\Stress\board.json' --campaign 'D:\Stress\CAMPAIGN_A' --stage 1 --prepare --dry-run
& $MON stress run --plan 'D:\Stress\plan.json' --board 'D:\Stress\board.json' --campaign 'D:\Stress\CAMPAIGN_A' --stage 1 --prepare
& $MON stress summarize --campaign 'D:\Stress\CAMPAIGN_A'

原生内置 profile 与 Monitor 配置的区别

CPU 原生名称：idle、integer、floating_point、matrix、memory、mixed、burst、thermal、stress_extreme。前六类分别对应空闲/整数/浮点/矩阵/内存/混合实现；burst 通过占空比交替，thermal 和 stress_extreme 通过持续时长及工作量增强。

GPU 原生名称：idle、ui_burst、game_light、game_mid、game_heavy、alu、sfu、texture、fill、mixed、burst、thermal、stress_extreme。原生 API 默认 null；idle/ui_burst/burst 及 game_light 的分数占空比不能直接用于当前 Vulkan 后端。Monitor 中的 light/mid/heavy 重新固定 duty_cycle=1。ALU/SFU 原生默认 compute，而 Monitor 明确改为 offscreen。不能仅看同名 profile 就认为后端或覆盖相同。

NPU 原生名称：kws01、ic01、ad01、sww01、framework_smoke。每个真实模型在 Monitor 中分 smoke、load、qualification 三类，后三种类别的证据要求不同。framework_smoke 仅是测试夹具。

使用选择

  • 初接板卡先跑对应 smoke，核对退出码、FINAL、完整收集和哈希。
  • 先跑一般 CPU/GPU 负载，再运行整数/浮点/矩阵/内存及 GPU 各 shader；每项保留单独 test/attempt。
  • 热稳态或突发用例与稳态性能基线分开统计；吞吐波动不是自动等同计算错误。
  • NPU 先核实运行库和厂商执行位置。没有运行库时记录跳过；null 结果不能填作 NPU 压测完成。
  • 未准备严格 golden 的 GPU 用例应跳过并记录原因；不能悄悄改成 verify_mode=none 后沿用正确性结论。

用例原理详解与源码索引

本文依据随包源码说明实际执行行为。链接为相对文件路径，解压后保留 npu-monitor 与 npu-workload 相邻结构即可离线跳转。用例参数全表见用例总表。

1. 三类工作单元和校验

CPU 以 batch 为工作单元，GPU 以 frame/dispatch 为工作单元，NPU 以 inference 为工作单元。初始化、预热、正式测量、校验、summary 和清理分开。工作单元真实完成后才增加计数；verify_interval 选择校验点，success_log_interval 只控制成功日志抽样，失败立即输出。

源码：CPU runner、GPU runner、NPU runner、校验调度。

checksum 相同只说明所比较的结果相同。CPU 初始化时可计算本次期望值，NPU 缺少外部 golden 时可用首次输出作重复一致性参考；正式独立正确性需要可信条件建立的参考。GPU 图像逐字节校验要求相同 shader、参数和产物。哈希不能证明硬件执行位置。

2. CPU 各计算核

整数运算链

执行原理：IntegerKernel 以 seed 初始化三个 uint64 状态；每次迭代做乘加、异或、循环移位与右移，最后用 Mix64 合并。后一轮依赖前一轮状态，因此它主要形成确定性的整数运算链。threads 指定独立 worker，每个 worker 使用不同派生种子。

参数与压测：iterations 增加每 batch 工作；threads 增加并行 worker。working_set_kb 不控制这个核的数组，因为此实现不使用工作集数组。

记录与边界：看 batch_count、operations_per_sec_avg、batch_time_ms_p99 和首次 checksum 失败。operation_count 是软件估算操作数，不是硬件退休指令计数；不保证覆盖所有整数指令或 SIMD。

源码：integer_backend.cpp；并行工作与结果归并见 RunWorkers。

双精度浮点递推

执行原理：FloatingPointKernel 用三个 double 状态反复做乘加与差分，越界时缩放或平移以保持数值范围。结尾 memcpy 取浮点位模式，经 Mix64 生成 checksum。其结果依赖运算次序与编译器浮点选项。

参数与压测：iterations 增加递推长度，threads 增加并行 worker。改优化等级或浮点选项后需重新核对可信参考。

记录与边界：看持续吞吐、batch 尾延迟与校验；源码没有显式向量 intrinsic，不可由名称宣称覆盖 NEON/FMA 的全部路径。

源码：floating_point_backend.cpp；并行工作与结果归并见 RunWorkers。

小型稠密矩阵乘法

执行原理：MatrixKernel 为 A/B/C 分配 double 数组，用确定性种子填充 A/B。以 row/column/k 三重循环执行 C 的乘加；重复之间保留很小的旧 C 分量。最终对全部 C 的位模式归并 checksum。维度由 working_set_kb 推算，并限制在 8 至 64；重复次数约为 iterations/(n*n)，至少一次。

参数与压测：working_set_kb 在维度上限内影响 n，超过上限不会继续扩大矩阵。iterations 控制重复次数，threads 并行执行独立矩阵。每次 batch 都包含该核中的分配、填充和归并。

记录与边界：看矩阵吞吐和 batch 延迟；这是普通软件循环，不调用 BLAS 或专用矩阵指令，不等同 NPU 矩阵单元测试。

源码：matrix_backend.cpp；并行工作与结果归并见 RunWorkers。

状态驱动随机读改写

执行原理：MemoryKernel 按 working_set_kb 为每个 worker 分配 uint64 数组，至少 128 元素。每轮从状态和 accumulator 生成索引，读取该位置、更新校验累加值并写回新值。结束时从最多 64 个分散位置继续归并。访问地址依赖先前结果。

参数与压测：working_set_kb 改变每 worker 数组大小；threads 会增加总工作集。iterations 控制随机访问次数。要判断落在哪级缓存，需要结合实际缓存容量与测量。

记录与边界：看吞吐/延迟及 checksum；该实现不是顺序带宽基准，也不是遍历每个 bit 的完整内存故障算法。

源码：memory_backend.cpp；并行工作与结果归并见 RunWorkers。

整数、浮点与随机访存混合

执行原理：MixedKernel 在同一循环交织 uint64 线性递推、位移/异或、状态索引的数组读写与两个 double 的乘加。结束时取最多 32 个数组样本和浮点位模式形成 checksum。它直接实现混合核，没有依次调用整数、浮点、矩阵、内存四个后端。

参数与压测：threads/iterations/working_set_kb 分别影响并行数、循环长度和每 worker 数组；改变任何一项都会改变工作/参考身份。

记录与边界：看温度、实际频率与吞吐变化；mixed 不包含 MatrixKernel，不能代替独立 matrix 用例。

源码：mixed_backend.cpp；并行工作与结果归并见 RunWorkers。

空闲与框架对照

执行原理：NullBackend 不执行真实 CPU 算法，runner 按 profile 的占空比与进展规则运行。idle 配置用于连接、生命周期与日志对照。

参数与压测：duty_cycle=0 形成空闲对照；需要真实压力时选择 integer/mixed 等后端。

记录与边界：框架通过不计为有效计算负载；软件等待不能证明 CPU 已进入某个硬件低功耗状态。

源码：null_backend.cpp；并行工作与结果归并见 RunWorkers。

突发、持续升温与高强度

burst/thermal/stress_extreme 是负载组织与参数预设，不是新的计算核。当前 CPU 对应配置使用 mixed：burst 让活跃与休眠交替，thermal 延长测量时段，extreme 增加迭代与工作集。休眠与负载结束处会产生间隔，不能把多个短运行的墙钟总跨度当作连续满负载时长。

源码：内置预设、占空比与停止条件。Monitor 参数见 cpu_burst_qualification_kirin9030.json、cpu_thermal_qualification_kirin9030.json、cpu_stress_extreme_qualification_kirin9030.json。

3. GPU 各图形路径

Monitor 当前 Vulkan profile 使用 mode=offscreen。后端创建离屏 RGBA8 目标，提交全屏图形绘制，等待 GPU，读回输出供校验。它不通过屏幕呈现来衡量 FPS；主机提交/等待/读回开销和有效 GPU 时间分别看待。后端选择逻辑见 backend_factory.cpp，图形资源和提交见 vulkan_graphics_backend.cpp。

ALU

执行原理：每个片段从 uv 和常数初始化 vec4，在 iterations 循环内执行分量乘加、fract 和分量重排。前后迭代相互依赖，形成持续向量算术。

压测与边界：增加像素数与 iterations 增加算术量；具体指令仍由着色编译器决定，不能直接对应硬件端口覆盖。

源码：workload_alu（搜索函数名 workload_alu）；全屏顶点输入见 fullscreen.vert。

SFU

执行原理：以 uv 生成两个状态，在循环中交替 sin/cos 并使用更新后的状态，输出其绝对值与 fract 组合。

压测与边界：用于观察超越函数密集路径；sin/cos 的硬件实现由驱动决定，不代表已隔离某个专用 SFU。

源码：workload_sfu（搜索函数名 workload_sfu）；全屏顶点输入见 fullscreen.vert。

纹理

执行原理：每个片段在 iterations 外循环内计算偏移，内循环按 texture_count 对同一个 sampler2D 做多次 texture 采样并累加，更新 uv，最后归一化输出。

压测与边界：texture_count 是同一纹理重复采样倍率，不是纹理对象数。纹理尺寸、缓存、过滤与坐标影响瓶颈；不自动等同纯显存带宽测试。

源码：workload_texture（搜索函数名 workload_texture）；全屏顶点输入见 fullscreen.vert。

填充

执行原理：直接把 uv 组合成 RGBA 输出写入离屏渲染目标，片段运算很少，主要用分辨率增加片段与写入规模。

压测与边界：这个函数没有 iterations 循环，调大 iterations 不增强此路径。总开销仍有提交、等待、图像转换与读回。

源码：workload_fill（搜索函数名 workload_fill）；全屏顶点输入见 fullscreen.vert。

混合与 light/mid/heavy

执行原理：在同一片段循环交织向量算术、sin/cos 偏移、纹理重复采样、fract 和通道混合。light/mid/heavy 是分辨率、循环次数和采样倍率的预设。

压测与边界：不是实际游戏帧；同名 profile 在原生默认与 Monitor JSON 中参数可能不同，使用实际 JSON。thermal/extreme 同样复用此 shader 增强时长或规模。

源码：workload_mixed（搜索函数名 workload_mixed）；全屏顶点输入见 fullscreen.vert。

compute、OpenCL、GLES 与 null 的区别

Vulkan compute 和 OpenCL 的 texture_like 通过计算模拟数据行为，不等于上述 texture() 图形采样。GLES 使用自身图形实现。虽然原生工程有多个后端，Monitor 是否允许配置还受校验和设备能力约束；不能把源码里存在后端等同已经完成其板端接入。null 用于主机框架自检，不提交真实 GPU 工作。

源码：Vulkan compute、OpenCL、GLES、null。

4. NPU 模型与推理路径

真实后端动态加载 TFLite C runtime，创建模型与 interpreter，挂接厂商 delegate，分配张量并检查类型、维度和字节大小，写入固定输入，提交调用、等待并读回输出。runner 当前逐次提交后等待，再进入下一次推理；不是多请求并行流水线。

INT8 输入/输出是量化张量，量化比例与零点由 manifest 定义。checksum 比较输出字节，不通过分类正确率或应用级准确率判断。固定样本反复推理有利于复现与输出一致性检查，但不能代表多输入、多形状、全部算子或所有工作集规模。

源码：runtime/delegate 与张量拷贝、资产与张量核验、输出校验、注册张量契约。

KWS01：关键词识别

张量：INT8 输入 [1,49,10,1]，490 字节；INT8 输出 [1,12]，12 字节。

原理与覆盖：输入是已准备的 MFCC 特征窗口，模型输出分类分数。每次重复使用同一窗口；不包含实时采音、特征计算、关键词数据集准确率统计。

配置与资产：manifest（张量/量化/资产哈希）、模型与输入目录；Monitor 示例 npu_kws01_load.json。

压测时观察 inference_count、verify_count、host latency、超时及实际 NPU 利用率/厂商诊断。inferences/s 不等于 TOPS；未提供可信设备耗时时保持不可用。

IC01：图像分类

张量：INT8 输入 [1,32,32,3]，3072 字节；INT8 输出 [1,10]，10 字节。

原理与覆盖：输入是模型边界上的小型 RGB 图像张量，输出类别分数。推理不包含摄像头、图像解码、缩放或完整视觉应用链路。

配置与资产：manifest（张量/量化/资产哈希）、模型与输入目录；Monitor 示例 npu_ic01_load.json。

压测时观察 inference_count、verify_count、host latency、超时及实际 NPU 利用率/厂商诊断。inferences/s 不等于 TOPS；未提供可信设备耗时时保持不可用。

AD01：异常检测

张量：INT8 输入 [1,640]，640 字节；INT8 输出 [1,640]，640 字节。

原理与覆盖：输入与输出均为特征向量，反复执行特征重建模型并比较输出字节。工具不独立计算异常评分阈值、ROC 或数据集检测精度。

配置与资产：manifest（张量/量化/资产哈希）、模型与输入目录；Monitor 示例 npu_ad01_load.json。

压测时观察 inference_count、verify_count、host latency、超时及实际 NPU 利用率/厂商诊断。inferences/s 不等于 TOPS；未提供可信设备耗时时保持不可用。

SWW01：唤醒词单窗口

张量：INT8 输入 [1,30,1,40]，1200 字节；INT8 输出 [1,3]，3 字节。

原理与覆盖：输入为已处理的单窗口特征，输出三类分数。当前 runner 的工作单元是一次窗口推理，不能据此宣称覆盖连续音频流、跨窗口状态和完整唤醒链路。

配置与资产：manifest（张量/量化/资产哈希）、模型与输入目录；Monitor 示例 npu_sww01_load.json。

压测时观察 inference_count、verify_count、host latency、超时及实际 NPU 利用率/厂商诊断。inferences/s 不等于 TOPS；未提供可信设备耗时时保持不可用。

smoke、load 与 qualification

三个用途复用相同模型配置与公共 Monitor 流程：smoke 为 null 资产/生命周期检查；load 为真实 delegate 重复调用，缺少外部参考时仅能做运行内一致性；qualification 额外要求可信 golden、逐次校验和绑定的厂商执行证据。

fallback_used=false 只能表明 runner 没有主动回退。厂商 delegate 可能接管部分算子，因此必须从厂商诊断确认执行位置，不能靠调用成功推断 full_npu。完整要求见 NPU 适配与资产/位置检查、NPU 资格化证据检查。

5. 如何按原理选择压测

先用 smoke 建立链路，再分别运行定向核/图形路径/模型，最后增加时长和强度。只改变一个工作量维度便于解释瓶颈；每次保留实际配置、资产哈希、板卡条件和首错。各定向用例的通过不能推导芯片全部单元覆盖，热持续用例也需实际温度趋势确认是否稳定。

Windows Linux 统一编译指南

入口和目标

在 workload 根目录使用 build.ps1（Windows PowerShell）或 build.sh（Linux/WSL），统一参数由 scripts/build.py 解析。CPU/GPU/NPU 使用同一交接源码目录中的编译入口。各子项目旧入口保留，集中入口为交接时推荐入口。

参数用途
--components 'cpu,gpu,npu'选择组件；还可选 relay、monitor；all=三类 workload 加 relay
--target host当前主机架构，不能部署成 Android/OHOS ARM64
--target android-arm64Android NDK 交叉编译，需 CMake/toolchain
--target ohos-arm64OpenHarmony/HarmonyOS NDK 交叉编译，需 CMake/toolchain
--engine auto/cmake/directauto 优先 CMake；host 可使用 g++/clang++ 直接编译
--gpu-apis 'null,vulkan'显式选择 GPU 后端；默认 null 只做框架验证
--configuration Release/Debug优化/调试构建，分别记录输出
--ndk-root PATH也可使用 ANDROID_NDK_HOME 或 OHOS_NDK_HOME
--compiler PATH / --c-compiler PATHdirect 模式的主机 C++/C 编译器
--generator Ninja指定 CMake generator
--cmake-arg=-DNAME=VALUE传递 SDK、库或项目专属 CMake 参数
--test执行短主机检查；交叉编译目标禁止在主机执行
--doctor检查本次选择需要的环境，不运行编译器
--dry-run生成 planned 构建计划；不产生成功产物或伪造哈希
--monitor-root PATHMonitor 目录，默认 sibling npu-monitor

PowerShell 中组件列表建议加引号，避免逗号被解释为数组。Windows 没有 POSIX termios，不能构建原生 Windows relay；用 WSL 的 host 自检或安装 NDK 后构建板端 relay。

主机环境

Windows 需要 Python 3.10+ 和可用的 C++17 编译器（例如 MSYS2 UCRT64 的 g++）；使用 CMake 时还需对应 generator/build tool。Linux 需要 Python 3、g++/clang++，relay 需要 cc/gcc/clang。运行 Monitor 测试需要 requirements.txt/requirements-dev.txt 中的 Python 依赖。

$env:PYTHON = 'C:\Path\To\python.exe'
.\build.ps1 --components 'cpu,gpu,npu' --target host --engine direct --doctor
.\build.ps1 --components 'cpu,gpu,npu' --target host --engine direct --test
PYTHON=python3 sh build.sh --components cpu,gpu,npu,relay --target host --engine direct --test

默认 GPU=null、NPU 的 native 测试=null/fake runtime。它们用于配置、生命周期和协议检查，不能当作实际 GPU/NPU 板端压测。--test 的 GPU 自检需保留 null 后端；编译真实 Vulkan 可同时启用 null,vulkan。

Android 和 OHOS 目标

目前交接机器没有两类 NDK，以下为配置好环境后的入口，尚未在本机完成交叉编译验收。缺失 SDK/toolchain 会明确失败，不会偷偷生成 host 程序冒充 ARM64。

$env:ANDROID_NDK_HOME = 'C:\SDK\android-ndk'
.\build.ps1 --components 'cpu,npu' --target android-arm64 --engine cmake --generator Ninja
$env:OHOS_NDK_HOME = 'C:\SDK\ohos-sdk'
.\build.ps1 --components 'cpu,gpu,npu,relay' --target ohos-arm64 --engine cmake --gpu-apis 'null,vulkan' --generator Ninja
export OHOS_NDK_HOME=/opt/ohos-sdk
sh build.sh --components cpu,gpu,npu,relay --target ohos-arm64 --engine cmake --gpu-apis null,vulkan --generator Ninja

CPU/NPU 使用各自 CMake toolchain；GPU 使用统一后的 standalone CMake。GPU 真后端还需要目标 SDK 的 EGL/GLES/Vulkan/OpenCL 头文件和库；Vulkan shader 构建需主机 glslangValidator。Android/OHOS 的双框架工程若在其他仓库，需要独立核对，不能把本入口当作该工程的替代品。

relay 使用目标 NDK clang/sysroot。脚本按 Android 的 LLVM prebuilt 或 OHOS native/llvm 布局定位；SDK 布局不符会拒绝执行，应核对实际 SDK 后调整，而不是套用主机 cc。

NPU 的编译不需要厂商库参与链接（运行时动态加载），但真实推理必须在板端具备 TFLite C runtime、厂商 delegate 和依赖库。构建成功不代表这些库存在或能运行。

输出与部署

每次输出独立目录：build/unified/<target>/<configuration>/<UTC时间-随机ID>/。其中有每组件日志、实际 binary、build-manifest.json，记录命令 argv、host/target、NDK 路径、返回码、产物大小和 SHA-256。failed/planned 与 success 明确区分。

只有 device target 的产物才进入 Monitor tools。不要把 host.exe 或 WSL ELF 放到手机。NPU 可使用 Monitor 的 scripts/stage_npu_assets.py 完整复制四模型；CPU/GPU 二进制、SPIR-V 和 relay 分别按平台配置准备。之后执行 --capabilities、deploy、verify-deployment；检查必要的校验能力。保留构建 manifest 与设备部署 manifest，作为源码到板端文件的对应依据。

Monitor 打包可选 --components monitor --target host --monitor-root PATH，依赖当前主机 Python 的 PyInstaller、pyserial、PyYAML，以及已准备的 release assets。它只生成当前主机的 Monitor 包；首次交接建议先执行 Monitor 的 validate --package 和原有打包脚本的完整检查。设备 workload 和主机 Monitor 的架构是不同维度。

沿用原 Monitor 打包脚本

使用 Monitor 原有 scripts/build.ps1 与 vmin_judge.spec，产物名称为 dist/vmin_judge.exe。CPU/GPU 的默认打包调用保留；包含 NPU 时使用原脚本的可选开关：

# 从 npu-monitor 目录执行，先准备真实板端 tools 资产与开发依赖
.\scripts\build.ps1
.\scripts\build.ps1 -IncludeNpu

脚本执行主机测试、发布资源校验、PyInstaller 构建及程序入口检查；新增压测命令通过主入口正常导入并随原打包方式收集，配置继续由原 config 资源目录携带。使用者无需安装 Python。发布人员应将可编辑 config 副本与程序一并提供；厂商库按项目部署方式准备，不能假定自动取得厂商依赖。

可执行文件内使用 stress validate-plan 和 stress run --dry-run 检查压测入口。主机构建检查与板端验收分别记录。没有 NDK 和真实板端资源时，不能用主机 null/fake 程序替代发布资产骗过打包校验。

压测工具设计指南

结构与责任

系统分为主机 Monitor、板端 device agent、原生 workload 和独立遥测四部分。Monitor 负责配置、身份与资产、启动事务、UART 判定和证据归档；workload 负责执行真实工作和输出原生 JSONL；agent 负责进程生命周期、完整本地留证和紧凑 UART 转发；telemetry 从平台声明的真实接口采样。外部电压/频率/系统调度不在本工具的写入控制范围。

主机 profile 与平台配置
  -> validate / probe
  -> 显式 deploy / verify-deployment
  -> run manifest 与唯一 test_id / attempt_id
  -> transport 启动板端 agent
  -> CPU batch / GPU frame / NPU inference
  -> 完整原始日志留板端，紧凑事件经 UART v2 到主机
  -> PolicyEngine 判定，collect 核验，report / 压测汇总归档

扩展点与兼容性

src/target_adapters.py 采用静态注册表，集中描述工作单元、吞吐/延迟字段、NPU 配置及资产/执行证据差异。CPU/GPU 保留原逻辑，不为三个 target 复制三套传输或判定引擎。新增目标时先添加适配器、schema、资产解析和测试，再接入同一公共流程。

CPU/GPU/NPU 的 C++ 公共代码各自维护，通过相同校验语义与适配层接入公共流程。三份 verify_schedule.h 需保持一致，并由测试检查。原生事件、校验能力与串口协议各自负责兼容性检查，不应互相替代。

workload 的执行模型

CPU 一次 batch 执行确定性计算；GPU 一次 frame/dispatch 提交并等待 GPU 操作，图形路径可读回图像；NPU 一次 inference 经过 Init/CreateResources/SetInputs/Submit/Wait/ReadOutputs/Destroy 生命周期。NPU 接口异步，但当前 runner 每次提交后等待完成，没有并发推理吞吐流水线。

工作量和日志是不同控制面。verify_interval 选择真实工作单元的校验点，计数只在实际校验路径增加；成功事件采样和每秒上限只限制日志。任何失败立即报告，并在 agent 侧锁存首个失败，防止后续没有 summary 时丢失。

预热不进入正式计数，golden 生成也不是持续性能样本。NPU 用预热次数，CPU/GPU 用预热秒数。吞吐保留原单位，设备时间没有有效证据时保持缺失。心跳只能代表已有进展，不能用后台定时线程把后端卡死伪装成健康。

资产与基准身份

部署清单必须能追踪 binary、生效配置、shader、manifest、模型、输入及 runtime/delegate 依赖。NPU manifest 的资产路径要受限，注册张量描述必须一致，声明 SHA-256 必须匹配。运行库可以是受管理资产或板端已安装且固定哈希的文件；不能将 Windows DLL 或主机 ELF 当作板端 SO。

生效设备路径配置与用户源码配置分别保留。修改配置/模型/输入/编译器选项/运行库后，原 golden 或性能基线是否仍匹配由 fingerprint 检查，不能靠重命名文件复用。NPU 正式参考要求生成条件和审批信息，执行位置要求独立厂商诊断绑定；无证据为 unknown。

传输和判定

设备完整 events/workload/summary/stderr/telemetry/FINAL 在 spool 留存。UART 只携带必要字段；长分区描述、模型信息不挤入单帧。COBS、CRC、序号、会话身份和 FINAL 规则共用，verification_summary 可以分片，主机合并并拒绝矛盾重复字段。

PolicyEngine 保留计算失败与基础设施错误的区别。缺依赖、部署/哈希错误、协议异常或证据不完整不应等同芯片算错；明确校验失败和 workload 失败必须保留。性能异常还要联系温度、实际频率、系统竞争和后端等待，不应仅用 throughput 下降推断硬件失稳。

集中构建和压测工具

workload scripts/build.py 只编排编译命令，不修改计算核。它支持显式组件、host/Android/OHOS、GPU API 选择，按每次构建记录命令、工具和产物。dry-run 产物是 planned，不是 success；未配置 NDK 不回退到 host 冒充交叉编译。Monitor 打包是主机组件，与设备 binary 分开。

Monitor src/stress.py 经可执行文件 stress 入口提供顺序执行；scripts/soak.py 为兼容入口。它，不是多负载联合调度器。它显式调用 validate/可选 deploy/verify/run/collect/report，追加记录每一次尝试。只有 PASS 且收集哈希完整的结果能归入完整通过项；框架后端、主机等待、预热与缺失 summary 不补算成压力时长。续跑根据计划/板卡配置身份和完成证据判断，重试保留新记录。

维护顺序

修改配置或接口先补有意义的边界测试，再跑相关协议、资产、agent/UART 和主机回归。新增实际硬件后端必须验证真实运行位置、输出与退出、阻塞调用/清理边界，以及设备收集。代码测试、模拟 runtime、实机运行和资格化结论分别记录。原始证据不可因测试失败而删除或覆盖。
