# 压测工具使用指南

## 先确认目标

这份指南用于手头板卡的负载运行和稳定性观察。记录 SoC/板卡型号、序列号、系统/驱动版本、供电和散热、操作者、是否已有外部锁频。工具不提供调压/锁频/休眠控制。不同板卡不能仅因为“都能 hdc 连接”而共用 Kirin9030 的身份、串口和遥测配置。

## 安装和目录

Monitor 主机依赖在 requirements.txt 中。把对应 SDK 编出的 CPU/GPU/NPU、relay 和 shader 放入 tools 的平台配置路径。NPU 模型和输入必须连同 manifest 相对布局一起保留。负载协议统一为 2；通过各 binary 的 `--capabilities` 输出检查 workload 类型、模式和特性，不从文件名猜版本。

复制现有 platform/profile 到新名字后适配新板卡：身份字段来自真实设备、传输选择 hdc/adb、UART 候选和波特率按接线确认、CPU/GPU/NPU 遥测路径按实际系统核对。Monitor profile 的 platform 字段和板卡记录一致。不要仅删除 identity.required 来让错误平台通过；未知接口先标为可选/不可用，并写清影响。

## 一次运行的完整步骤

以下为 PowerShell 示例，设备 ID 和串口必须替换。Linux 使用相同 Python 参数，PC 串口通常是 /dev/ttyUSB*；所有全局参数放在子命令前。

```powershell
python main.py validate --profile cpu_smoke_kirin9030
python main.py --transport hdc --device DEVICE_ID probe --platform kirin9030
python main.py --transport hdc --device DEVICE_ID deploy --profile cpu_smoke_kirin9030
python main.py --transport hdc --device DEVICE_ID verify-deployment --profile cpu_smoke_kirin9030
python main.py --transport hdc --device DEVICE_ID --pc-serial COM4 run --profile cpu_smoke_kirin9030 --test-id BOARD_A_D1 --attempt-id A001 --pc-artifacts full --telemetry
python main.py --transport hdc --device DEVICE_ID collect --test-id BOARD_A_D1 --attempt-id A001 --artifact-set full --verify-hashes
python main.py report --run-dir output/BOARD_A_D1/A001 --format markdown,json,csv
```

deploy 显式准备文件，verify-deployment 核验文件，run 只检查和执行已部署资产。更换 profile、二进制、shader、模型、输入或生效配置时重新部署核验；不要把先前用例的成功状态带入另一个用例。

每次测试使用稳定 test_id 分组、唯一 attempt_id 记录一次尝试。正式一周记录选择 `--pc-artifacts full` 和完整 collect，保留原始输出。脚本或命令失败时仍尽可能 collect 原 attempt；重试生成新 attempt，保留第一次失败现场。

## CPU GPU NPU 的选择

CPU 先 smoke，再 integer/floating_point/matrix/memory/mixed，最后 burst/thermal/extreme。threads、iterations、working_set_kb 控制工作量；Monitor 不强制 CPU affinity，实际跑在哪些核需遥测/系统记录核实。thermal 运行长不等于已达到热稳态，观察温度斜率与降频情况。

GPU 先 smoke/load_light，再 mid/heavy、ALU/SFU/texture/fill。Monitor 当前 Vulkan 走 offscreen RGBA8，不能直接使用原生 idle/burst/compute/分数占空比设置。load-only 使用 none 时只判显式错误；有同配置可信 golden 后才能运行严格 golden-image 并作正确性判断。texture_count 的含义和 fill 对 iterations 的限制见用例总表。

NPU 先 smoke 校验资产和链路，再在运行库准备完成后尝试 kws01，再扩展 ic01/ad01/sww01。缺少 runtime/delegate 时记录未执行；不要用 null 结果替代真实 NPU。qualification 还要求外部已批准 golden、逐次校验和绑定的厂商执行位置证据，详见中文 NPU 专项指南。

## 正确性与性能

- `verify_interval` 控制实际校验，不是日志间隔；`verify_count` 必须来自 workload 真实执行。
- `success_log_interval` 控制成功校验事件采样，额外有每秒限流；失败立即输出。
- summary 缺失、计数矛盾、FINAL 缺失、身份/CRC/序号错误或部署哈希错误，都不能当作合格样本。
- 没有外部 golden 的重复一致性不等于独立正确性；none 模式不检查输出正确性。
- CPU operations/s、GPU frames/s、NPU inferences/s 不可直接按数值比较。
- 预热和 golden 生成不计入正式测量；device_time_valid=false 时设备耗时保持不可用。

## 失败和现场处理

| 现象 | 先看什么 | 处理方向 |
|---|---|---|
| 配置/部署失败 | validate/verify-deployment 返回、资产路径与 SHA | 先修资产/平台/依赖，不记录为芯片计算错误 |
| checksum/图像不匹配 | 首次 verify 失败、对应 golden/config/binary | 保留现场，核对参考身份，固定条件重复 |
| hang/无 summary | 最后真实 heartbeat、workload/stderr、relay/FINAL | 判断 workload 卡死、驱动等待、串口或 transport 中断 |
| 吞吐下降 | 温度/频率/利用率、host/device latency | 检查降频、热稳态、系统竞争和锁频是否真正生效 |
| collect hash 不符 | artifact-hashes.json 与缺失文件 | 证据不完整，不能用缺失记录证明 PASS |
| NPU 部分执行 | 厂商诊断、partition、运行库身份 | 未证明完整执行时标 unknown/partial，不推导 full_npu |

默认遇到失败先停，记录故障时间、板卡状态、操作者动作，再决定是否续跑。不要自动清空日志、重启后只留下成功结果，或删除设备 evidence 来节省空间。若主机进程被强制终止，需要人工核对板端进程是否确已结束。

## 重放和报告

```powershell
python main.py simulate --profile cpu_qualification_kirin9030 --events PATH_TO_EVENTS
python main.py simulate --profile npu_kws01_smoke --raw-serial PATH_TO_CAPTURE
python main.py report --run-dir PATH_TO_RUN --format markdown,json,csv
```

重放是已有证据的确定性检查，不会补齐原来丢失的设备文件。报告与原始结果应同时保留；后生成的报告不能覆盖设备原始日志。NPU profile 重放也会核对实际校验次数。
